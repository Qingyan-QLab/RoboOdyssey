## 1. 定位、输出与规划原则

Benchmark 接收场景包、冻结 sequence、被测模型与运行配置，执行连续评测，输出证据、评分、诊断和报告。
它同时维护供另外两库调用的公共能力，但不生成任务内容、不维护 Oracle 决策策略或训练数据业务。

| 仓库 | 独有责任 | 输出 |
|---|---|---|
| SessionBuilder | 场景准备与理解、任务设计、预计状态推演、生成质量与人工审核 | 场景包、冻结 sequence、审核资料 |
| Benchmark | 模型接入、正式评测、实验生命周期、评分、结果比较与诊断；公共能力维护 | 执行记录、评测结果、报告、公共接口 |
| DataSynth | Oracle 策略、参考执行、恢复、噪声扰动、筛选、批量生成与训练导出 | 参考计划、实际示范、扰动样本、训练数据 |

目标代码依赖为 `SessionBuilder → Benchmark`、`DataSynth → Benchmark`，两生成库之间通过产物衔接。
只有 Benchmark 计划开源，必须在不安装两生成库的环境中安装、校验发布数据并完成评测。
公共模块先随 Benchmark 包提供；CPU 数据处理与 Isaac 依赖分开加载，不增加第四仓库或服务。
已统一：发行名 `RoboOdyssey`、导入名 `roboodyssey`、版本 `0.2.2`，消费者依赖 `>=0.2.2,<0.3`；公共 API 见 [PUBLIC_API](PUBLIC_API.md)。

优先级统一为：**P0 最小正确闭环与行为基线；P1 质量、规模和工程化；P2 能力扩展与研究项**。
处理方式统一为“保留／完善／重设计／新增／迁移”；已有实现不会因出现在规划中自动列为新增。

## 3. Benchmark 独有功能目标

| 工作包 | 功能目标与处理方式 | 可检查的验收结果 |
|---|---|---|
| BF1 模型接入 | 完善现有适配；统一协议版本、动作／问答能力声明、记忆重置、观测帧引用和输入权限检查；保留通用自定义 Agent 入口 | 脚本 Agent 覆盖正常、unsupported、错误 JSON／request_id、错误帧引用、超时；至少验证现有 SimpleNav 与视觉 API 两种适配；模型输入无私有 GT／参考／内部可见性证据 |
| BF2 实验管理 | 从 SimpleNav 专项启动整理通用实验描述，模型启动由适配层提供；冻结数据选择、配置、种子、预算、运行身份；先支持串行批次，再考虑并发 | CPU 预检不启动模型／Isaac；计划中每条 sequence 均有终态；不同尝试独立保存；托管／外部服务生命周期明确；同一配置可重建完整启动命令 |
| BF3 中断与异常 | 保留现有停止和清理；区分模型不支持、任务失败、协议异常、仿真崩溃、证据缺失与人为中断；增加有上限的序列级重试 | 注入超时、进程退出、STOP 和日志缺失后，失败不消失、不冒充任务排除或完成；重试从规范初始状态和空模型记忆开始，关联原尝试并保留其记录；无自有残留进程 |
| BF4 指标与版本 | 保留成功率和部分分；完整定义任务／Session／sequence 聚合与缺失值；版本化成功规则、评分、参考算法和动作模型；扩展指标需独立提案 | 固定证据集在线／离线结果一致；排除因果、分母和缺失参考均可查；原始结果不覆盖；不支持的旧版本明确拒绝；新版本差异有逐任务解释 |
| BF5 结果比较 | 新增按同一场景／sequence 配对的多模型、多种子、多配置比较；输出总体与任务类型、长程跨度等分组结果 | 数据哈希、规则、动作／本体、观测预算等不匹配时拒绝直接合并正式分数；报告缺失任务、失败尝试、样本数和配对差值；统计估计标明方法与样本单位 |
| BF6 失败诊断 | 完善现有报告，串联公开请求、修补理由、实际目标、动作、状态变化与视频；区分模型、任务适配、环境和证据问题 | 固定失败样例能定位到任务／事件／帧；没有证据的原因标为未知；诊断评分不冒充正式分；仅凭保存产物可重建报告，不重新执行任务 |
| BF7 可复核与独立发布 | 完善来源记录和最小样例，覆盖 CPU 安装、正式运行、原记录复核与新尝试重跑；统一公开包与兼容导入入口 | 按声明的源码包／wheel 形态在干净环境安装，不安装 Builder／DataSynth；从源码目录外完成 CPU 检查；公开样例和脚本 Agent 可在声明的 Isaac 环境执行完整 sequence；产物搬移后可复核，资源路径不依赖私有工作区 |

物理中途恢复属于另行研究项，不是 BF3 的默认承诺。报告重建、证据重算、从头重跑、恢复物理 checkpoint
是四种不同能力，输出必须声明实际提供哪一种。现有 reset 仅重置机器人，不恢复物体、历史或模型记忆。
新指标的业务定义与首次正式启用仍需审阅；发布形态所需的脚本、适配示例和可分发场景必须包含在验收范围。

## 4. 公共数据：输入、输出与兼容含义

本节是三库共同约定的维护入口，正式字段后续进入数据文档和校验器；本轮不修改已有归档。

| 数据 | 必须表达的内容 | 生产／消费边界 |
|---|---|---|
| 场景包 | 场景身份与版本、资产依赖、语义／名称、规范初始状态、环境设置、资源哈希；派生地图注明本体和生成条件 | Builder 准备；三库经公共入口读取 |
| Sequence | 场景版本绑定、Session／Task 顺序、公开请求、私有目标／历史绑定、环境变化、能力要求、生成及审核来源 | Builder 生成并冻结；Benchmark／DataSynth 读取 |
| 运行配置 | 本体与控制、抓放／碰撞、传感器、预算、采样时钟、随机种子、规则及算法版本 | 两执行方分别选择用途配置，共同验证 |
| 执行记录 | 运行／尝试身份、任务修补、拟动作／实际动作及反馈、观测引用、实际状态／历史、事件因果、时间与终态 | 公共执行流程记录；评分、诊断、DataSynth 导出消费 |
| 参考数据 | 场景／sequence／状态绑定、计划或执行标记、算法／策略版本、可恢复的计算输入、扰动及筛选来源 | 公共参考计算／DataSynth 产生；不得覆盖冻结任务 |

“旧数据兼容”主要指已有场景和任务归档，不是模型权重，也不是把训练对话格式统一为评测输入。
下面几种版本解决不同问题，不能互相代替：

| 版本维度 | 当前含义／例子 | 兼容时必须检查的内容 |
|---|---|---|
| 数据字段 schema | `cl_task_sequence_v1` 的 `schema_version=5` | manifest、公开任务、私有目标等结构与字段；各类场景／结果 manifest 有自己的 schema，不能一概写成 5 |
| 文件布局 layout | `layout_version=2`：集合下 `scene_versions/<revision>` 被 `sequences/<id>` 共享；layout 1 为每序列自带输入的旧布局 | 文件位置、资产引用、场景绑定和哈希；改目录不自动升级任务语义 |
| 运行契约 runtime | `contextual_requests` v3 | 请求、名称、历史依赖、任务修补与环境变化的解释规则 |
| 结果／指标版本 | 例如结果 schema 与 `progress_path_v4` | 原证据是否足够、原评分实现是否可用、比较是否具有相同口径 |
| 训练导出版本 | 例如 Builder 现有 `robot-agent-message-v3` | 由 DataSynth 适配，与冻结 sequence 的 schema／layout 分开管理 |

用户已确定兼容范围：**三个仓库当前输出互通即可**。公共入口只接受 sequence
**schema 5 + layout 2 + runtime v3**，场景版本使用其独立 schema。已实现集合/tar、独立场景版本、
显式场景绑定的 detached sequence；不调用 Builder 编译器。Builder 历史 layout/runtime 转换、旧编译器完整
重新生成审计均不属于本轮承诺；历史研究入口保留不等于三库支持这些旧格式。

对象 ID、单位、坐标、动作含义、时间基准和公开字段白名单统一定义；大资产按版本共享，结果另存。
评分比较另核对数据选择、成功／排除规则、指标、参考、动作／本体、观测和预算配置；包版本相同不足以证明可比。

## 5. 共享能力目标与接口边界

下表为目标边界；已经落地的公开入口、参数和限制以 [PUBLIC_API](PUBLIC_API.md) 为准，其余仍是规划。公共能力的实现和规则测试归 Benchmark 所有。

| 工作包 | 公共能力及建议接口 | 责任边界与交付要求 |
|---|---|---|
| B1 数据入口 | `load_scene`、`load_sequence`、绑定校验、归档读写、版本适配 | 不生成任务／样本；CPU 可用；脱离生成器读取冻结数据；公开与私有内容分开校验 |
| B2 状态与规则 | 状态创建／分支／快照／提交、历史查询、名称、请求修补、碰撞与可达性查询 | 世界事实与任务经历分开；预计和实际状态有明确类型／来源；输入同规则版本时采用同一实现；生成器可叠加保守候选策略 |
| B3 环境、执行与采集 | 环境创建／关闭、动作执行、状态回读、采样、策略适配、基础事件记录 | 在线成功判定驱动终止和真实历史；数值评分及报告独立消费证据；Oracle 私有适配器不能扩大模型输入权限 |
| B4 参考归并 | 迁入 DataSynth 通用导航、搬运成本、答案计算及测试；版本化查询接口 | 只读快照，计划不证明执行；旧评分算法保留，新 restools 算法独立选择；参考输入可恢复，摘要只用于校验 |
| B5 三库联调 | 固定场景、连续 sequence、成功／失败／环境变化样例 | 验证产物互读、权限、状态连续和版本绑定；独立发布验收不依赖私有库安装 |
| B6 本体与控制扩展 | 按 [MOTION](MOTION.md) 增加身体轮廓、运动约束、抓放控制和对应参考 | P2 独立能力版本；动作规则、候选、碰撞和评分同步验证，不能把显示本体替换写成真实控制已完成 |

状态变化带前后版本、原因和来源事件。动作结果以执行后回读为准；预计变化只提交到预计分支。
物体、门或持物变化使相关地图、碰撞、路径缓存失效；不可变场景数据共享，候选分支不无条件复制全部资产与历史。
任务内与跨 Session 的实际历史由公共执行流程维护；Builder 的“假设成功”记录不能注入执行历史。

相机和环境持续复用，图像、深度、位姿、帧号、时钟和状态版本一起关联；原始帧存储按用途配置。
正式评测仍遵守现行墙钟观测规则；采集开启、编码、背压和漏采必须记录，不以离线补帧伪造实时观测。
当前正式模式不启用诊断录像；新增采集配置不能未经验证改变正式输入或预算。

额外环境扰动由 DataSynth 设计，公共环境执行并回读。任务开始后若世界变化导致冻结评分参考不可比较，
必须显式标记评分不适用／缺失或使用新规则版本，不能默默按旧参考打分，也不能因此删去失败样本。
问答现场观察可以作为 DataSynth 示范质量配置；是否升级正式成功规则仍待决定。

## 6. 统一优先级、依赖与交付顺序

ID 保留原 B1–B5 含义，BF 为独有功能工作包，编号不表示严格串行。下方阶段表仍列完成条件，实际状态如下。

| 工作包 | 当前完成与证据 | 尚未关闭的验收项 |
|---|---|---|

## 7. 验收证据与运行成本

| 验证层 | 必备样例／指标 | 通过标准 |
|---|---|---|
| CPU 数据与规则 | 当前格式、哈希破坏、场景错配、未知版本、预计分支、实际失败历史 | 正例按冻结规则解释，反例明确拒绝；没有私有库或 Isaac 导入依赖；无预计成功混入实际历史 |
| 评分回归 | 导航有序进度、搬运、问答、reset、排除、缺失参考、混合版本 | 保持行为的工作包逐任务与基线一致；新规则有独立版本和差异报告；在线与离线复核一致 |
| 真实执行与权限 | 同一 sequence 跨 Session；前序失败、持物／门变化、任务修补、独立 sequence 重置 | 实际回读与事件一致，后续历史正确；公开适配输入无私有证据；原始帧与状态引用可解析 |
| 异常与发布 | 超时／退出／停止、部分日志、干净安装、公开样例 | 每条计划运行有终态；无静默丢任务和自有残留进程；不安装两生成库也能校验、执行、分析 |
| 性能与规模 | 固定硬件、地图／任务数；启动时间、参考可用率、搜索次数、p95 采样／动作延迟、漏帧率、峰值内存、写盘量 | 先记录原基线并冻结允许上限，再判断验收；保持行为的重构不能无说明降低参考可用率或增加漏帧；未定上限的性能项不得标完成 |

参考计算必须覆盖常见分辨率和抓取域，不只覆盖“大场景”：当前 DataSynth 默认每目标最多 256 候选，
0.1 m 栅格上空旷的 1.5 m 抓取域约 700 个候选，可能在搜索前即预算耗尽。B4 必须验证此类普通配置，
并区分不可达与 `indeterminate`；不能只增加预算或静默抽稀后仍声称同一参考模型。
采集性能使用固定动作脚本比较开启／关闭原始存储的影响；相机复用本身不能证明墙钟观测时序不变。
验收记录包含输入哈希、版本、环境、命令、产物位置、失败项及解释；CPU、Isaac、模型集成证据分别报告。
